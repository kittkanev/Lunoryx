# Локальная аутентификация паков — разработка 1.4.0

Новые игры используют контейнер `LNXPCK02` с HMAC-SHA-256. Это разработка 1.4.0, а не описание опубликованных бинарников 1.3.1. Новых криптографических зависимостей и сетевых сервисов нет.

Один раз создайте **новый** внешний файл ключа:

```sh
./engine --generate-package-key /private/location/game.key
```

Команда использует системный генератор случайных чисел, записывает ровно 32 сырых байта, задаёт доступ только владельцу (в Windows также System/Administrators) и не перезаписывает существующий файл. Храните ключ вне папок проектов, `Runtime/`, app bundle и релизных архивов. Не коммитьте его. Нужна защищённая офлайн-копия: без утраченного ключа аутентифицировать собранные с ним игры нельзя.

Выберите **Game / Build → External package key file** либо передайте путь явно:

```sh
./engine --package-key-file /private/location/game.key --build-game project.lunoryx Game
./Game --package-key-file /private/location/game.key
./Game --package-key-file /private/location/game.key --verify-package
./engine --package-key-file /private/location/game.key --verify-package Game
```

Переменная `LUNORYX_PACKAGE_KEY_FILE` задаёт ту же локальную настройку; явный `--package-key-file` имеет приоритет. Выбор ключа относится к процессу: он не сериализуется в проект, не копируется в игру и не выдаётся через Lua/MCP API. Произвольный доверенный C# сохраняет права пользователя и может читать доступные ему файлы; это не гарантия изоляции секрета средствами ОС.

В Windows используйте `Lunoryx.exe`/`Game.exe`. Для Mac передайте параметр в `Game.app/Contents/MacOS/Game` либо настройте переменную окружения перед запуском. В Linux/macOS входной ключ должен быть обычным файлом только для владельца (`chmod 600`). Для обычного редактора/MCP без загрузки или сборки пака ключ не нужен.

Проверяются домен HMAC, все значимые поля футера, длина и содержимое манифеста и весь payload. HMAC и итоговые ассеты используют одни и те же захваченные байты ресурсов. Ограниченная валидация манифеста может отклонить неверные данные до сравнения тега; загрузка проекта, извлечение managed runtime и старт скриптов происходят только после успешной аутентификации всей транзакции. Неверный/отсутствующий/повреждённый ключ, плохой тег и старый CRC-only `LNXPCK01` отклоняются, прежний результат не заменяется. Старые редактируемые проекты — отдельная миграция; игры пересобираются из проекта новым runtime с ключом.

HMAC — **симметричный MAC**, а не публичная цифровая подпись. Любой владелец ключа может и проверять, и подделывать паки. HMAC не шифрует содержимое, не удостоверяет нативный runtime/издателя и не запрещает повтор старого корректного пака. Windows Authenticode и Apple Developer ID/notarization — отдельные задачи CI; без настоящих credentials/evidence они не заявляются.

Лимиты сохранены: 1 GiB payload, 128 MiB runtime template, 4096 ресурсов вместе с проектом и 4 MiB манифеста. CRC32 остаётся только в отдельных корзинах дедупликации с последующим побайтовым сравнением. Стресс-тесты проверяют sparse-аутентифицированные паки размером 1 GiB−1, ровно 1 GiB и отказ выше лимита.

Активный ключ защищён от записи/удаления средствами редактора и выбора как выхода игры. При сборке runtime/ресурсов файл ключа отвергается; сырые байты ключа проверяются в итоговом потоке, включая стыки буферов/ресурсов. Фоновые задачи завершаются до уничтожения состояния ключа/I/O. Это не запрещает пользователю или доверенному C# с OS-доступом намеренно раскрыть секрет в другом представлении.
